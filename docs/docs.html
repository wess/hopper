Documentation

Hopper is a native macOS app that both manages Docker and provides it. This covers installing it, running its own engine, pointing the docker CLI at it, migrating off Docker Desktop, and building from source.

Install

The simplest path is Homebrew:

brew install --cask wess/packages/hopper

Or download Hopper.dmg from the latest release, open it, and drag Hopper.app to Applications. The build is signed with a Developer ID and notarized, so Gatekeeper opens it without a fuss.

Requirements. Apple Silicon (arm64). Apple Containers needs macOS 26 or later — the vmnet APIs that container-to-container networking depends on do not exist before it. On an older macOS, Hopper still works against a Docker engine you already run.

First run

On launch Hopper picks an engine. On macOS it prefers Apple Containers and falls back to any engine you already run — Docker Desktop, Colima, Rancher Desktop, or a remote daemon over TCP. On Linux it looks for Docker or Podman, checking rootless sockets before the system ones.

If Apple's container is not installed, Hopper says so and offers to get it: it downloads the package Apple signed and hands it to the system installer, which asks you to approve it. Hopper never elevates privileges itself.

Once it is there and autostart is on (the default), Hopper starts Apple's services in the background and the status footer moves from starting to connected. You can control this under Settings → Engine.

The engine

On macOS the engine is Apple's container: every container is its own lightweight VM, and Apple maintains it. Hopper installs it, starts and stops its services, and drives it.

It is not the Docker Engine API, and Hopper does not pretend otherwise. Apple's runtime publishes no Docker socket — the request for one was closed as not planned — so Hopper speaks to it through the container command instead. Some things simply are not there:

  • pause and unpause, and renaming a container;
  • changing a container's CPU or memory after it is created;
  • restart policies and --hostname;
  • healthchecks, so no container reports a health state; and
  • Compose, and the live event stream (Hopper polls instead).

Hopper hides those rather than offering a button that always fails. If you need them, switch to a Docker engine under Settings → Engine.

Two things worth knowing about Apple's volumes: a named volume is a real ext4 filesystem, so it arrives with a lost+found directory — Postgres needs PGDATA pointed at a subdirectory — and anonymous volumes are not removed with their container.

Import from Docker

Import finds Docker Desktop, Colima or Rancher Desktop and copies your images, networks and containers into whichever engine Hopper is running. Containers are recreated rather than moved: the image, ports, mounts and labels travel, and a writable layer is by definition scratch. Nothing is removed from the source, so if the import goes wrong your Docker install is exactly where it was.

The source engine is pinned when you scan, so a daemon coming up or down mid-import cannot quietly redirect it somewhere else. Per-item failures are reported and the rest continues — one unreadable image should not cost you the other nineteen.

Already running Docker Desktop? On macOS Hopper prefers its own engine by default. To have it manage your existing daemon instead, set the engine preference to existing in Settings, or launch with HOPPER_ENGINE=existing.

Find images

The Registry tab searches public registries for images to pull. Type a term and switch between Docker Hub and GitHub — each hit shows its stars, an official marker where it applies, and the exact reference Pull will fetch (nginx, ghcr.io/owner/app). Search talks to the registries directly, so it works before an engine is even up; the pull lands the image on the Images tab. Private and rate-limited pulls use whatever credentials you have stored.

Detail pane

Selecting a container opens a pane beside the list with five tabs:

  • Logs — live streaming, demuxed stdout/stderr, with stderr coloured.
  • Stats — CPU, memory (page cache excluded), network, block-IO, and PIDs.
  • Files — browse the container's filesystem and copy files out.
  • Terminal — a real interactive shell over a hijacked socket, with a terminal model that interprets escape sequences.
  • Inspect — the full JSON tree.

Streams are cancelled by closing the pane or switching containers — there is no separate abort registry to fall out of sync with what is on screen.

Docker CLI

Hopper serves the Docker API at a unix socket, so any tooling can target it:

export DOCKER_HOST="unix://$HOME/.hopper/run/docker.sock"
docker info
docker compose version

Or create a Docker context named hopper so docker and docker compose target it by default. Hopper ships the Apache-2.0 docker CLI in the app bundle, so uninstalling Docker Desktop does not take your docker command with it.

Tools that hardcode /var/run/docker.sock (Testcontainers, socket-mounting sidecars) ignore Docker contexts. Settings offers an opt-in compatibility symlink for those; it is off by default because the path is machine-wide.

Bind mounts

Apple's runtime bind-mounts host directories directly (--volume /host/path:/in/container), so there is no share list to maintain. Two caveats: only ro is honoured as a mount option, and a bind mount performs worse than a named volume, so put databases on volumes.

MCP server

Hopper ships a standalone Model Context Protocol server that exposes Docker tools to AI clients over stdio:

hoppermcp        # or: cargo run -p mcp

It offers list/start/stop, logs, and system-info tools. A failed tool call is reported inside the result rather than as a protocol error, so a client does not retry something that cannot succeed.

Build from source

Hopper is a Cargo workspace — Rust throughout.

cargo run -p app            # launch (dev binary: hopperdev)
cargo test                  # the whole suite
cargo clippy --all-targets  # lint
cargo run -p mcp            # the MCP server

A source build behaves exactly like the shipped one. Hopper runs no VM of its own any more, so it needs no entitlement and no code-signing dance to reach its engine — Apple's container does the virtualizing, under its own privileged helpers. To produce a signed, notarizable bundle:

scripts/bundle.sh           # assemble + sign dist/Hopper.app
scripts/dmg.sh              # package dist/Hopper.dmg

Architecture

The workspace is layered bottom-up; each crate depends only on those below it, and the gpui-free core never imports gpui.

model     shared domain types (the wire contract)
store     ~/.hopper/ JSON persistence + OS keychain
docker    Engine API client (hyper) + every domain module
apple     Apple Containers, driven through the `container` CLI
engine    provider abstraction; Apple / Docker-or-Podman / existing
migrate   Docker → Hopper import
host      the async service facade the UI calls
mcp       the stdio MCP server
app       the gpui + guise application

Hopper speaks to two kinds of engine, behind one enum in host::runtime: the Engine API over a socket, and Apple's runtime over its CLI. An enum rather than a trait because the streaming calls take closures, which are not object-safe.

The async layer runs on a Tokio runtime; gpui has its own executor. They meet at one seam — app::bridge — which runs a future on Tokio and delivers the result on the gpui main thread. This mirrors the tables architecture.

Releasing

A workspace version bump in Cargo.toml pushed to main is the release. CI runs the full gate (tests, clippy -D warnings, a release build), produces a signed and notarized Hopper.dmg, publishes the GitHub release, and updates the Homebrew cask.
