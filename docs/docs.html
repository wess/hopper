Documentation

Hopper is a native macOS app that both manages Docker and provides it. This covers installing it, running its own engine, pointing the docker CLI at it, migrating off Docker Desktop, and building from source.

Install

The simplest path is Homebrew:

brew install --cask wess/packages/hopper

Or download Hopper.dmg from the latest release, open it, and drag Hopper.app to Applications. The build is signed with a Developer ID and notarized, so Gatekeeper opens it without a fuss.

Requirements. Apple Silicon (arm64) and macOS Sonoma or newer. The managed engine needs Apple's Virtualization framework, which is Apple-Silicon only.

First run

On launch Hopper picks an engine. On macOS it prefers its own managed VM engine and falls back to any engine you already run — Docker Desktop, Colima, Rancher Desktop, or a remote daemon over TCP.

The managed engine needs a small guest image (a kernel and initramfs). The release bundles it, but if it is ever missing — a lean install, a stripped bundle — Hopper fetches it once, on the first start, from its own release: a ~120 MB download, checksum-verified before it boots, and cached under ~/.hopper/ for every run after. So a Mac with no Docker at all still ends up with a working one.

If Hopper is providing the engine and autostart is on (the default), it boots the VM in the background; the status footer moves from starting to connected once dockerd answers. You can control this under Settings → Engine.

The managed engine

On a Mac with no Docker installed at all, Hopper still gives you a working Docker. It:

  • acquires its guest image if it is not already on disk — bundled with the app, or downloaded and verified on first start;
  • boots a minimal Linux guest (a raw arm64 kernel and Alpine initramfs) on Virtualization.framework, entirely from Rust;
  • runs dockerd inside it and bridges its socket out to ~/.hopper/run/docker.sock;
  • forwards published container ports to localhost; and
  • shares host directories into the guest so bind mounts work.

Resources (CPU, memory, disk) and the shared-directory list live in Settings. CPU and memory apply on the next engine restart; the data disk is a sparse file created once at ~/.hopper/engine/ and never recreated, so your images and volumes survive upgrades.

Already running Docker Desktop? On macOS Hopper prefers its own engine by default. To have it manage your existing daemon instead, set the engine preference to existing in Settings, or launch with HOPPER_ENGINE=existing.

Detail pane

Selecting a container opens a pane beside the list with five tabs:

  • Logs — live streaming, demuxed stdout/stderr, with stderr coloured.
  • Stats — CPU, memory (page cache excluded), network, block-IO, and PIDs.
  • Files — browse the container's filesystem and copy files out.
  • Terminal — a real interactive shell over a hijacked socket, with a terminal model that interprets escape sequences.
  • Inspect — the full JSON tree.

Streams are cancelled by closing the pane or switching containers — there is no separate abort registry to fall out of sync with what is on screen.

Docker CLI

Hopper serves the Docker API at a unix socket, so any tooling can target it:

export DOCKER_HOST="unix://$HOME/.hopper/run/docker.sock"
docker info
docker compose version

Or create a Docker context named hopper so docker and docker compose target it by default. Hopper ships the Apache-2.0 docker CLI in the app bundle, so uninstalling Docker Desktop does not take your docker command with it.

Tools that hardcode /var/run/docker.sock (Testcontainers, socket-mounting sidecars) ignore Docker contexts. Settings offers an opt-in compatibility symlink for those; it is off by default because the path is machine-wide.

File sharing

Bind mounts only reach the container for directories Hopper shares into the guest. Your home directory is shared by default; add others under Settings → File sharing. A bind mount outside a shared path shows the container an empty directory rather than your files — Hopper warns when it detects one.

Migrate in

Hopper can move your existing Docker world over. It scans for a source engine — Docker Desktop, Colima, or Rancher Desktop — lists what it holds, and copies your selection (images as tar streams, volumes through a helper container, networks recreated) into Hopper's engine, streaming progress. The source is pinned at scan time, so a daemon coming up or down mid-migration cannot redirect it.

MCP server

Hopper ships a standalone Model Context Protocol server that exposes Docker tools to AI clients over stdio:

hoppermcp        # or: cargo run -p mcp

It offers list/start/stop, logs, and system-info tools. A failed tool call is reported inside the result rather than as a protocol error, so a client does not retry something that cannot succeed.

Build from source

Hopper is a Cargo workspace — Rust throughout.

cargo run -p app            # launch (dev binary: hopperdev)
cargo test                  # the whole suite
cargo clippy --all-targets  # lint
cargo run -p mcp            # the MCP server

On macOS, cargo run -p app brings up the real managed engine: a cargo runner (scripts/dev/run.sh, wired in through .cargo/config.toml) signs the dev binary ad-hoc with the virtualization entitlement, and the engine downloads its guest image on first start — so a source build is a working Docker, not just a manager for one you already run. To build the guest image yourself and produce a signed, notarizable bundle:

scripts/build/guest.sh      # guest kernel + initramfs (Linux/buildx)
scripts/bundle.sh           # assemble + sign dist/Hopper.app
scripts/dmg.sh              # package dist/Hopper.dmg

Architecture

The workspace is layered bottom-up; each crate depends only on those below it, and the gpui-free core never imports gpui.

model     shared domain types (the wire contract)
store     ~/.hopper/ JSON persistence + OS keychain
docker    Engine API client (hyper) + every domain module
engine    provider abstraction; the macOS VM (objc2)
migrate   Docker Desktop → Hopper migration
host      the async service facade the UI calls
mcp       the stdio MCP server
app       the gpui + guise application

The async Docker layer runs on a Tokio runtime; gpui has its own executor. They meet at one seam — app::bridge — which runs a future on Tokio and delivers the result on the gpui main thread. This mirrors the tables architecture.

Releasing

A workspace version bump in Cargo.toml pushed to main is the release. CI runs the full gate (tests, clippy -D warnings, a release build), builds the guest image, produces a signed and notarized Hopper.dmg, publishes the GitHub release, and updates the Homebrew cask.
